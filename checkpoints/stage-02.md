# Звіт-контрольна точка: етап 2

**Тема:** валідація запитів і узгоджений формат помилок  
**Варіант:** `devices`  
**Статус:** виконано за видимими тестами  
**Дата:** 2026-10-06

## Мета

Додати валідацію JSON і полів запиту, коректну класифікацію помилок для ідентифікатора та відсутнього ресурсу, а також єдиний JSON-формат відповіді помилки згідно з [README.md](../README.md).

## Що реалізовано

- У [internal/handler/device.go](../internal/handler/device.go) реалізовано перевірку тіла створення та заміни:
  - тіло має бути коректним JSON-об’єктом; порожнє тіло, зіпсований JSON, масив, `null` та додаткове JSON-значення після об’єкта відхиляються;
  - обов’язкові `name`, `serial`, `manufacturer`, `type` перевіряються на наявність, рядковий тип і непорожнє значення після обрізання пробілів для перевірки;
  - `warranty_months` приймається як ціле число або `null`/відсутнє поле; `comment` — як рядок або `null`/відсутнє поле.
- Помилки запиту повертаються як JSON `{"error":{"code":"...","message":"..."}}` з `Content-Type: application/json`. Текст внутрішньої помилки декодування клієнту не передається.
- ID для GET, PUT і DELETE перевіряється як десяткове число в межах `uint32`. Некоректний ID повертає `400 invalid_id`; коректний ID без ресурсу — `404 not_found`.
- Для PUT дотримано порядок перевірок: ID → тіло → наявність ресурсу.
- Невідомі маршрути також повертають JSON-помилку `not_found` через [internal/app/app.go](../internal/app/app.go).
- Успішні PUT і DELETE ще не реалізовані — це частина етапу 3.

## Перевірки

Виконано:

```text
gofmt -w internal/handler/device.go internal/app/app.go
go test ./internal/app -run TestStage2 -v
go test ./internal/app -run 'TestStage1|TestStage2' -v
go vet ./...
```

**Результат:** усі Stage 2 тести пройшли; спільний запуск Stage 1 і Stage 2 також пройшов; `go vet ./...` завершився без зауважень.

Повний `go test ./...` та `go test -race ./...` не запускалися: етапи 3–5 іще не реалізовані, тому вони не є критерієм завершення цього етапу.

## Що перевірено тестами

Видимі тести покривають відсутні/порожні обов’язкові поля, некоректний JSON, порожнє тіло, JSON-масив, неправильні ID для GET/PUT/DELETE, відсутній ресурс, порядок перевірок PUT і JSON-заголовки/формат помилок.

Контракт README також враховано в реалізації для пробільних рядків, `null`, неправильних типів полів і меж `uint32`; ці граничні випадки не всі мають окремі видимі Stage 2 тести.

## Наступний крок

Етап 3: успішна повна заміна ресурсу через PUT, видалення через DELETE, збереження ID і `created_at`, оновлення `updated_at` та перевірки цих сценаріїв.
